# Milestone 3 — UI/UX Design System (spec)

Consolidates the UI/UX design-system wayfinder map (GitHub issue #55) and its eight resolved tickets: shadcn distribution research (#56), brand → token unification prototype (#57, merged via #91), component vocabulary + inventory grilling (#58), admin app shell + IA prototype (#59), landing refactor scope grilling (#60), brand identity grilling (#90), logo palette → token layer + atmosphere prototype (#92), and admin dashboard data-viz grilling (#93). Decisions were settled 2026-09-09 → 2026-09-14 (charting grilling, research, prototype reaction rounds, owner rulings). The milestone keeps its established name — **UI/UX Design System** — seated in the former Booking Availability slot (owner deferral 2026-09-09; nothing renumbers: Admin Auth stays M4, Admin CMS M5, Production Hardening M6). Published as GitHub issue #94; `docs/plan.md`'s Milestone 3 checkboxes were red-penciled to match (wayfinder ticket #61) on 2026-09-14.

## Problem Statement

The landing site is functionally complete but visually unsettled: its theme is TanStack Start starter carryover (never owner-decided), `packages/ui` was a dead tokens-only package while both apps duplicated the token block inline, and nine hand-built components carry no shared primitive foundation. The admin app is UI-greenfield — and about to generate dozens of CRUD primitives (tables, forms, dialogs) that overlap landing's needs, which the old "each app owns its UI" rule would duplicate and drift. Two editions now ship from one codebase: main's booking-present landing and the v1 booking-free artifact, so every shared surface needs designed variants for both. And the studio's actual brand — its logo palette — was never expressed in the product at all.

## Solution

One shared design system in `packages/ui`: the owner's logo palette as a validated oklch token layer (two fixed brand points — petrol primary and ink — plus four reference tones, a 50–900 ramp, states, and a wash-based canvas), the Figtree / Roboto Slab / Geist Mono trio self-hosted, and a shared shadcn/Base-UI primitive library generated by the CLI into the package (ADR-0017). Landing is reskinned onto the ruled atmosphere — ink-led header and footer bands, petrol-wash body with white cards and cool hairlines — with every shipped surface restructured per the landing-refactor rulings (new footer, hamburger mobile nav, full-width two-CTA hero, per-variant catalog affordances) and the booking wizard componentized with zero flow changes. Admin gets its decided shell: variant A labeled sidebar, collapsible to an icon rail, with the ruled nav taxonomy and a v2-stub dashboard. Both variants of every shared surface (main booking-present and v1 booking-off) land on system-styled ground. The starter's island palette and vocabulary die with the swap.

## User Stories

1. As a visitor, I want every page to share one visual identity — palette, type, spacing, components — so the studio reads as one professional brand.
2. As the studio owner, I want my logo's petrol and ink as the only fixed brand points, so the product's brand is mine, not a template's.
3. As a visitor, I want an atmospheric landing (ink bands framing a tinted wash body with white cards), so the site feels like a photography studio rather than a SaaS template.
4. As a visitor on a slow connection, I want all three typefaces self-hosted, so no render-blocking font CDN stands between me and the content.
5. As a visitor, I want text that meets WCAG AA on every surface it appears on, so I can read comfortably, including muted text on the tinted body.
6. As a keyboard user, I want visible focus styles on every control, including CTAs on the dark header band, so I can navigate without a mouse.
7. As a mobile visitor, I want a hamburger button that opens a collapsible panel carrying the full navigation, so I can reach any page on a small screen.
8. As a visitor, I want a footer on every page with the brand line, the four nav links, and a "Call or visit a branch" affordance, so contact is always one scroll away.
9. As a visitor arriving on the homepage, I want a full-width hero with a heading, a blurb slot, and two clear actions, so I immediately know where to go next.
10. As a visitor on main (booking-present), I want the hero's primary action to be "Book now", so the site's conversion path leads with booking.
11. As a visitor on v1 (booking-free), I want the hero to offer "Call Us" and "Services" instead, so the site still converts without online booking.
12. As a visitor browsing the packages index, I want cards that are CTA-less on v1, so the catalog reads as a showcase rather than a broken funnel.
13. As a visitor on a package detail page, I want exactly one primary action — "Book this package" on main, "Call us" on v1 — so the next step is unambiguous in both editions.
14. As a visitor on the services page, I want a quiet closing strip telling me to call or visit a branch, so I know how to proceed after browsing.
15. As a visitor reading the services page, I want copy that never presupposes online booking, so v1's pages don't promise what the artifact removed.
16. As a visitor on the branches page in v1, I want a "Call {branch}" phone CTA per branch, so contacting the right studio is one tap.
17. As a customer in the booking wizard, I want every step wearing the same brand system as the rest of the site, so the flow feels continuous, not bolted on.
18. As a customer, I want the wizard's progress indicator, choice cards, and hour grid rebuilt as real components without any behavior change, so the restyle costs me nothing in familiarity.
19. As a customer, I want a sticky summary rail and a clean confirmation card in the decided system, so my booking reads back clearly at every stage.
20. As a customer whose booking is rejected, I want the rejection card on a white surface with readable error styling, so I can see what to fix.
21. As a visitor on a package page that doesn't exist, I want the not-found state wearing the system, so even errors look cared for.
22. As a visitor viewing placeholder imagery, I want covers and slots that look intentional in the brand system, so the site holds up until real photography arrives (M5).
23. As a screen-reader user, I want the mobile menu and collapsible sidebar as proper disclosure navigation with current-page semantics, so the IA is navigable non-visually.
24. As a staff member, I want a labeled sidebar grouped by area — Overview, Catalog, Studio — so I always know where I am in the admin app.
25. As a staff member, I want to collapse the sidebar to an icon rail with tooltips, so tables and image-heavy editors get the full content width.
26. As a staff member, I want a sticky top bar with search and notifications, so context stays available while I scroll.
27. As a staff member opening the dashboard, I want an honest empty state saying the dashboard arrives with v2, so the shell's promise matches its content.
28. As a studio owner working in admin all day, I want admin tool-neutral — flat surfaces, brand reduced to wordmark and primary — so long sessions aren't fatigued by marketing atmosphere.
29. As a developer, I want one `shadcn add` target in `packages/ui` for shared primitives, so both apps use identical, drift-free components under one brand.
30. As a developer, I want one token file both apps import, so a theme change propagates everywhere at once.
31. As a developer, I want Tier-1 primitives named verbatim after their registry names, so upstream docs and CLI output map one-to-one.
32. As a developer, I want composed components app-local in PascalCase, so domain components stay next to the surfaces that use them.
33. As a developer, I want no shared-composed middle tier in v1, so the system stays two strict tiers until a third consumer actually appears.
34. As a developer building M4/M5 forms, I want TanStack Form + its Zod adapter + the `field` component as the decided pattern, so form validation UX is consistent and type-safe from the first form.
35. As a developer, I want `sonner` toasts and a mounted Toaster, so user feedback is uniform across admin.
36. As a developer, I want the starter's island palette and vocabulary removed with the swap, so stale tokens don't linger or collide with new ones.
37. As a developer, I want the booking wizard's `data-*` seams preserved verbatim through the restyle, so the existing verification scripts keep working.
38. As a developer, I want no chart tokens or chart vocabulary shipped now, so v2's data-viz decisions aren't preempted.
39. As a developer, I want a living token gallery during the build, so I can eyeball tokens and states while implementing.
40. As the owner, I want per-surface screenshots on both variants to accept before merge, so the shipped look is the one I ruled.

## Implementation Decisions

### Brand & the token layer (tickets #90, #57, #92)

- **Fixed brand points: primary `#06708e` (petrol) and ink `#0e131a` only.** White is the system constant (surfaces), not a brand point. The four other logo hexes — deep petrol `#084257`, light neutral `#dedede`, mid gray `#7e7f7f`, cool gray `#afb8ba` — are **reference tones**: recorded facts of the logo that derivations sit near, never load-bearing promises. Derivation adds tones around the fixed points; it never nudges them.
- **Strictly cool palette; no warm accent anywhere.** shadcn's destructive red stays the only warm semantic. Token names are neutral/functional (numeric ramp + functional atmosphere names) — the island vocabulary dies.
- **Typefaces: Figtree (sans), Roboto Slab (serif), Geist Mono (mono), self-hosted** (the current render-blocking Google Fonts `@import` for Roboto Slab + Geist Mono dies). **Headings stay sans everywhere** (settles #57's parked question): Figtree carries all headings and body; Roboto Slab ships in the token layer for later editorial/display use with no surface mandated this milestone.
- **One shared token source:** `@sevendays/ui/tokens.css`, imported by both apps' stylesheets. The **validated candidate from the #92 prototype branch (commit `9100672`) is the value source**: the six logo hexes as round-trip-verified oklch (hex kept as canonical comment per token), brand ramp 50–900 (hue held at the primary's 225.078; 600 is the primary), hover 700 / active 800 / focus-ring 400, an AA-safe derived muted text `#686969` (derived against the darkest wash, superseding the logo's mid gray for text), landing wash/surface tokens, and an admin tool-neutral semantic mapping (admin building green was the derivability gate). shadcn defaults stay untouched: radius scale, destructive, motion.
- **The swap:** the validated logo-palette layer replaces the interim teal preset (the #57 merged layer) as both apps' live theme in this milestone; after the swap the token file is maintained directly. The interim preset stays live on main until the swap lands (pre-launch site; nothing rips out early).
- **Atmosphere (owner-ruled mix):** header and footer are **ink-led bands** — brand-ink background, white text, petrol as the header's action color. The body is the **petrol wash canvas** (`--background` = the wash-base tone — owner-confirmed) with **white cards floating on it and cool hairline section separators**. Light-neutral gray is demoted to alternating **emphasis strips** (e.g. the closing "Call or visit a branch" strip). Deep petrol is an **accent only** (media gradients, CTA labels on white).
- **Dark `SiteHeader` variant:** the current component renders light; the milestone build adds the ink-led dark rendering.
- **Destructive placement:** shadcn-default destructive stays (4.77:1 on white); destructive-bearing text renders on white/card surfaces, never bare on the wash canvas (where it measures 4.44:1). Darkening the token was considered and rejected to keep the validated layer intact.
- **Focus-visible normalization:** all band CTAs (header/footer strips) get the focus-visible treatment the body CTAs already have.
- **Token occupancy:** `--surface-strong` collides with a starter island primitive of the same name — the island layer's removal clears the name as the new layer lands.
- **No `--chart-*` tokens ship.** The mono-primary chart-ramp direction (ramp of the primary) is recorded as steering for the future data-viz effort only (per #93).

### Distribution: `packages/ui` as the shared library (ticket #56 → ADR-0017)

- **The official shadcn monorepo pattern.** `packages/ui` becomes a real shared component library — primitives + semantic tokens + utils — with **one `components.json` per workspace** (both apps + the package), all three carrying the same `style` / `iconLibrary` / `baseColor` (pinned to the apps' current `new-york`/lucide/neutral posture — no style churn). The CLI routes generated primitives into `packages/ui` and app-composed blocks into the requesting app.
- **Base UI is the primitive base for all new components** (shadcn's default since 2026-07-02 — not Radix; installed skill prose saying otherwise is stale). No `@radix-ui` or `@base_ui` dependencies exist yet, so there is nothing to migrate.
- **`cn` comes from the `cn` package**, replacing the per-app hand-rolled `clsx`+`tailwind-merge` helpers (no third copy).
- **AGENTS.md's "each app owns its UI" rule is amended** (with this spec) to: shared primitives + semantic tokens live in `packages/ui`; brand and page-specific components stay in each app. ADR-0017 records the ruling and the alternative considered (per-app generation; namespaced private registry — the latter's revisit trigger is a third consumer).
- **Two strict tiers (ticket #58's vocabulary):**
  - **Tier 1 — primitive:** shared, in `packages/ui`, `shadcn add`-generated on the Base UI base, **registry names verbatim** (`button`, `card`, `dialog`, …).
  - **Tier 2 — composed:** app-local, PascalCase domain names (`PackageCard`, `PackageForm`, …), composed on Tier 1 + the shared token layer.
  - **No shared-composed middle tier** in v1 — no shared DataTable wrapper, no shared EmptyState. Revisit only if a third consumer appears (same trigger as a namespaced registry).

### Landing refactor, surface by surface (ticket #60)

- **Scope/look split:** #60's rulings are structural and look-neutral; the #92 atmosphere skins them. **Imagery stays placeholder** — no real studio-imagery hunt this milestone (real imagery is M5's R2 business).
- **Shared chrome:** new `SiteFooter` on all surfaces (above). `SiteHeader` keeps its desktop row; **mobile = hamburger + collapsible panel** (owner overrule). Not-found/error surfaces are ride-along chrome: the package not-found gets full system treatment (its page is touched anyway); router defaults only where trivially cheap.
- **Home:** a distinct **full-width hero band** (heading + two CTAs + blurb slot) above the strips; main's CTAs are "Book now" (primary) + "View services" (secondary), mirroring v1's ruled "Call Us" + "Services". Strip order unchanged (featured → services teaser → branches); one consistent section rhythm across strips.
- **Catalog affordances** (discretion delegated by the booking-off direction ruling, issue #72): `/services` gains one quiet closing strip "Call or visit a branch" → `/branches`, call-or-visit flavored; its "attach to your booking" line rewrites neutrally. `/packages` index stays CTA-less. `/packages/:slug` gains **exactly one primary affordance per variant** — main "Book this package" → `/book?package=<id>` (the prefill search params already exist; zero flow change), v1 "Call us" → `/branches`. Both styled by this milestone; the v1 pieces swap via the established scrub mechanism.
- **Component fate:** no consolidation, no renames; `WalkInBadge` becomes the thin `badge` wrapper; transients (`CoverPanel`, `HourChipGrid`) get token-fit restyle only.

- **Placeholder copy:** `/about` and the home blurb get skeleton polish (hierarchy, spacing, rhythm) with copy slots staying placeholder-marked — structure must not depend on copy that hasn't arrived. `/about`'s portfolio grid and testimonial slots survive as M5 drop-in slots.
- **Token gallery:** the `/prototype-tokens` showcase route stays during the milestone as the living token gallery; deleted at milestone close-out.

### Admin shell & IA (tickets #59 + #93)

- **Shell: variant A — labeled sidebar — with the sidebar collapsible** between the labeled posture and the icon-rail posture (tooltips + group dividers) via an owner toggle. Sticky top bar (search, notifications); left sidebar with grouped nav; user card at the bottom.
- **Nav taxonomy:** Overview (Dashboard, Appointments) · Catalog (Packages, Add-ons, Studio services) · Studio (Branches, Settings). Non-dashboard screens are **stubs naming their owning milestone** (M4 auth, M5 CMS incl. R2 uploads, v2 appointments dashboard) — clickable IA, not designs.
- **Dashboard: ships as a stub** (empty state, "arrives with v2") — no KPI cards, no filter bar, no appointments table, no `StatCard` in v1. Everything chart- or dashboard-shaped belongs to the v2 delivery-versions effort (spec issue #76).
- **Look:** admin wears the shared token layer's tool-neutral mapping — flat shadcn surfaces, brand reduced to wordmark + primary; the copied island CSS dies with the rest of the starter remnants.
- **Riding the build from the #59 prototype:** the collapsible-sidebar behavior and its deferred roughness minors (hoisting `currentTarget` out of state updaters, real nav semantics for the Catalog section, the dual `aria-current` cleanup, the catalog-toggle no-op).

### Quality bar (map charting rulings)

- **Dark mode is out** — light theme only for both editions; the token layer's `.dark` block is carried, parked, not judged.
- **Motion = shadcn defaults**; no custom motion system.
- **No Storybook, no visual-regression tooling.**
- **A11y = Base UI/shadcn defaults + keyboard and responsive passes** on what's built; no formal audit. WCAG AA on own surfaces governs the token derivation (the measured pair table rides the #92 prototype record).

### v1-variant coverage (ticket #60 + the booking-off direction)

Main lands booking-present; the v1 scrub's ruled content pieces — the "Call us" primary button, CTA-less catalog cards, the two-CTA hero, the `tel:` CTA on branch cards, the detail-page affordance — must land on system-styled ground. **This milestone styles those pieces; the established scrub mechanism swaps them.** Verification (below) runs on both variants. M3 build PRs go through the standing pick/skip/split discipline for the `v1` branch like every merge to main.

## Testing Decisions

Good tests here assert external behavior only — never module internals. This is a restyle-and-scaffold milestone, so the bar is **invariants preserved plus visual acceptance**, not new behavioral suites:

1. **Existing landing suites keep passing unchanged** — the lib-seam tests and any route-level suites are the proof that queries, API-client calls, and flow behavior didn't move. Same URLs, same server functions, same query factories.
2. **`data-*` seams preserved verbatim** (`data-step`, `data-strip`, `data-offering`, `data-back`) — the M2 CDP verification scripts (booking wizard, content pages) stay runnable read-only through the restyle; run them at build time as regression evidence.
3. **`packages/ui` joins the check pipeline** — lint/typecheck/build over its TypeScript source (utils, exports) like every other package; no component unit tests for Tier-1 primitives (shadcn-generated source, validated by use, owned upstream).
4. **`pnpm check` green for every touched app/package** — the standing repo gate.
5. **Visual acceptance is the owner's per-surface screenshots on both variants** (main booking-present + v1-scrubbed), judged against the #92 composition the owner already approved — screenshots confirm the implementation matches the ruled look.
6. **Contrast re-verification** where surfaces change: the AA pairs from the #92 measured table (ink-on-light, white-on-primary, link-on-white, muted-on-wash) re-measured if any value they depend on moves.

## Out of Scope

- **Booking Availability** — deferred by the owner (2026-09-09), v2's payload; the date/time step stays the past-datetime-floor placeholder (`HourChipGrid` transient).
- **Booking-flow UX changes** — frozen on the M2 map; this milestone componentizes and restyles only.
- **Real studio imagery** — M5's R2 business; imagery stays placeholder throughout.
- **Confirmation-email visual pass** — the M2 email is deliberately plain HTML (Workers constraint); whether it adopts the system is a later effort's call, not this milestone's.
- **Admin dashboard content** — KPI cards, tables, charts, chart tokens, chart vocabulary, multi-hue categoricals: all the v2 delivery-versions effort's (spec issue #76); the mono-primary ramp stands as steering only.
- **M4 auth mechanics and M5 CMS mechanics (incl. R2 uploads)** — their milestones decide those; this milestone delivers the shell + the component system they build with.
- **Dark mode, Storybook / visual-regression tooling, formal a11y audit** — ruled out at charting.
- **Rebranding** — identity is the owner's logo palette (fixed points + reference tones); the milestone never alters identity, only expresses it.
- **A shared-composed component tier** — banned until a third consumer appears.
- **Production hardening (M6)** — logging, Sentry, CORS, rate limiting, domains, email deliverability.
