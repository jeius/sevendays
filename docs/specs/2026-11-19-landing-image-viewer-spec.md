# Landing Image Viewer Spec

*Drafted 2026-11-19 from wayfinder map [jeius/sevendays#324](https://github.com/jeius/sevendays/issues/324) — the owner accepted all recommended answers at charting ([the charting record](https://github.com/jeius/sevendays/issues/324#issuecomment-6994349920)) and picked the library from the [researched shortlist](https://github.com/jeius/sevendays/issues/328#issuecomment-6995034844); the spec was drafted from those rulings as [issue #336](https://github.com/jeius/sevendays/issues/336) (resolving task [ticket #329](https://github.com/jeius/sevendays/issues/329)). Status: **owner-settled at charting + the pick, 2026-11-19**; not yet sliced into tickets — ready for a `/to-tickets` handoff. This document is the repo copy of issue #336.*

## Problem Statement

The landing's photographs are dead ends. The home gallery strip and the `/about` tabbed portfolio render the studio's work through the shared mosaic wall (`MosaicPhotoGrid` over the same `/api/v1/gallery` payload — the two surfaces speak one wall by the #164/#224 rulings), and the package detail renders its cover through the `CoverPanel` half of the ruled D2 split — but none of them open, zoom, or navigate. A visitor who wants a close look at a framed print, a caption's attribution, or a package's cover presentation has no path: the wall's images are bare `<img>` elements with no affordance, and the browser's fallback (right-click → open image) is not an experience the studio would design. Meanwhile every modern studio site opens its photographs in a lightbox; the wall just sits there. The charting grill ruled the fix and its exact scope: a Standard-set viewer on the two gallery surfaces plus single-image zoom on the package cover — nothing more.

## Solution

- **A click-to-view lightbox over the shared mosaic wall**, gained inside `MosaicPhotoGrid` so the home strip and the `/about` portfolio both get it free with unchanged call sites. The ruled Standard set: open on click; close via Esc / backdrop / ×; prev-next arrows + keyboard + swipe; counter; zoom (double-click / pinch, pan); captions render only where the data already carries them, as a simple line — no thumbnail strip, no fullscreen chrome.
- **The package-detail cover zooms as a lone image** — no prev/next on a single photograph, no counter.
- **The library is picked: yet-another-react-lightbox v3** (the #328 pick, from the #325 research shortlist) — MIT, zero runtime deps, React-19-official, SSR-clean by shipped-dist inspection, with the Zoom / Counter / Captions plugins carrying the ruled set (~15–19 kB gzip all-in); installed landing app-local per ADR-0017.
- **The chrome is theme-aware by law**: an immersive near-black stage in both themes (the recorded deliberate exception to token-riding), with token-native accents (the mono caption register, the brand focus ring).
- **The a11y law is real, not aspirational**: full keyboard operability, dialog semantics and focus-on-open from the library, focus-restore-on-close added by hand, `prefers-reduced-motion` respected natively.

## User Stories

1. As a customer browsing the home page, I want to click any gallery photograph to view it full-screen, so I can actually see the studio's work instead of squinting at wall thumbnails.
2. As a customer viewing a photo, I want to move between photos with arrows, keyboard, and swipe, so browsing the portfolio feels like a gallery rather than one image at a time.
3. As a customer viewing a photo, I want to zoom with a double-click or pinch and pan the zoomed image, so I can inspect the detail of a frame or a print.
4. As a customer viewing a photo, I want to close the viewer with Esc, the backdrop, or the ×, so dismissal is always one familiar gesture away.
5. As a customer on the counter, I want a "current / total" readout, so I know where I am in the set and how much is left.
6. As a customer on `/about`, I want a photo's caption shown in the viewer, so the context the wall gives carries into the close-up view.
7. As a keyboard-only customer, I want the viewer fully operable by keyboard — open, navigate, zoom, close — so my input method excludes me from nothing.
8. As a customer with reduced motion enabled, I want the viewer's transitions to calm down, so the site's motion doesn't follow me into the viewer.
9. As a customer on a package page, I want to zoom the cover photo, so I can judge the package's presentation — without being offered next/prev controls for a lone image.
10. As a customer on a slow connection, I want the first viewer open to be instant, so the close-up doesn't re-download what the wall already loaded.
11. As a customer on a phone, I want swipe navigation and pinch zoom to work natively, so the viewer feels like the phone's own photo app.
12. As a studio owner, I want the viewer chrome to feel native to the brand in both light and dark themes, so the close-up view doesn't break the site's voice.
13. As a studio owner, I want the viewer's captions governed by the same law as the wall's, so the home keeps its caption-free ruling and `/about` keeps its attribution line.
14. As a studio owner, I want no thumbnail strip and no fullscreen chrome, so the viewer stays the ruled Standard set and nothing more.
15. As an implementer, I want the library, posture, and configuration pinned in this spec, so nothing is re-litigated at execution time.
16. As an implementer, I want the slide mapping as one pure seam with pinned laws, so the alt and caption rules have a single source and a testable floor.
17. As an implementer, I want the viewer to live inside the shared mosaic component, so the two gallery surfaces cannot drift apart.
18. As a studio owner, I want to react to the rendered viewer before it is called done, so visual acceptance stays a real gate (the #94 amendment).

## Implementation Decisions

**D1 — Library + install posture.** `yet-another-react-lightbox` **3.33.x** (the v3 line — 3.33.1 at pick time): MIT, zero runtime deps, peer-supported through React 19, SSR-clean by shipped-dist inspection (a closed lightbox renders nothing during SSR; the portal mounts at runtime into `document.body`). Install **landing app-local** (`pnpm --filter @sevendays/landing add yet-another-react-lightbox`) per ADR-0017 — a landing-only viewer doesn't argue for a `packages/ui` seam; no other workspace touches it. Plugins carry the ruled set: **Zoom** (double-click / double-tap / pinch + pan), **Counter**, **Captions** — open / close / prev-next / keyboard / swipe are core behavior; the unruled plugins (Thumbnails, Fullscreen, Download, …) are simply never imported, so nothing unused ships. The rejected alternatives stand as recorded in the pick: PhotoSwipe (core release-frozen since 2024-05), the hand-rolled `dialog.tsx` baseline (the pinch/pan zoom engine is the costly piece), react-photo-view (zero ARIA in the shipped build, SSR-hostile portal), lightgallery + Fancybox (license-gated). **Static import, no lazy gate** — SSR-safe per the research verification, and the bundle rides only the routes that already render the wall/detail; the named escalation if the rendered-variants pass finds the chunk cost real is lazy-mounting the Lightbox on the open state — decide there, not now.

**D2 — Component placement.** One **`PhotoViewer`** composition (`apps/landing/src/components/photo-viewer.tsx`), landing app-local: props `slides` (YARL `Slide[]`), `index: number | null` (`null` = closed), `onClose`, and a `variant` for the per-surface option set (`mosaic` | `cover`). It owns the focus-restore effect (D7) and consumes the lib seam (D5). **`MosaicPhotoGrid` gains the viewer — it comes free on both surfaces** (charting ruling): the home gallery strip (`apps/landing/src/components/home-image-led.tsx:213`) and the `/about` portfolio (`apps/landing/src/routes/about.tsx:128`, the `data-portfolio-grid` slot) share the component over the same gallery payload, and **both call sites stay unchanged**. The package-detail cover (`apps/landing/src/components/package-detail.tsx`, the `CoverPanel` half) is the single-image variant.

**D3 — The mosaic composition (home + /about).** Each photo's `figure` gains a real `<button type='button'>` wrapping the `img` (the `figcaption` stays outside the button — button content must be phrasing-only). Click / Enter opens the viewer at that photo's index; the button gets `cursor-zoom-in`. The button's accessible name is the img's existing alt (`photo.title ?? 'Studio gallery photograph'` — the wall's alt law, unchanged and reused by the slide mapping). The `Reveal` stagger, span rhythm, row heights, and both empty-state laws are untouched — the button replaces the bare img inside the existing figure. **Captions follow the surface's existing law**: the component's `captions` prop already governs the wall's figcaption (home ruled OFF, about renders when present — #164 Round 2 / #224), and it governs the viewer's caption line the same way — `captions: true` surfaces map `photo.caption` into the slide's `description`; `captions: false` surfaces never set it. *Draft-time interpretation, flagged for the owner's reaction:* the charting text says "only where the data already carries them (the /about gallery)"; this spec reads that as the surface posture — the home viewer shows no captions so the viewer can't add what its wall was ruled not to show.

**D4 — The cover composition (single image).** The `CoverPanel` half gains the open affordance **only when `coverImageUrl` is set** — the initials placeholder is not a photograph and does not zoom. Single slide (`{ src: pkg.coverImageUrl, alt: pkg.name }`), plugins `[Zoom]` only. The lone image rules out navigation: `carousel={{ finite: true }}` (with one slide both arrows compute disabled — verified in the shipped build) and `render={{ buttonPrev: () => null, buttonNext: () => null }}` (the library's named hide — no arrows render at all). No Counter.

**D5 — Slide mapping (the pure seam).** `apps/landing/src/lib/viewer.ts` (plain lib-seam, the `gallery-tabs.ts` shape): `photoSlides(photos, { captions })` — `PublicGalleryPhoto[]` → YARL `Slide[]`: `src = photo.photoUrl`; `alt = photo.title ?? 'Studio gallery photograph'` (one source of the wall's alt law); `description = photo.caption` **only when the surface asks for captions AND the caption is non-null** (the plugin renders the description line only when the slide carries one — verified in the shipped build; no `title` element is ever set). The option vocabulary lives here as pinned constants (the lib house style): the cover variant's single-slide config (D4) and the shared `labels` strings. **The cache win, pinned in the seam's comment**: the slide `src` is the same URL the wall already rendered (`photoUrl` has no variants on the public wire), so the first viewer open is served from the browser cache — no second download of a "full-size" variant that doesn't exist. Accepted trade-off: the public gallery payload carries no image dimensions, so the library discovers dimensions on load (its loading placeholder covers the gap).

**D6 — Viewer configuration.** **Close gestures**: `controller={{ closeOnEscape: true, closeOnBackdropClick: true }}` — Esc is the library default; backdrop-close is the ruled gesture but **defaults `false` upstream**, so it is set explicitly; the × rides the default toolbar; pull-up/pull-down close stay at their `false` defaults — not in the ruled gesture set. **Carousel** (mosaic variant): library defaults — `finite: false` (the wall loops), `preload: 2`, `padding: '16px'`, `spacing: '30%'`, `imageFit: 'contain'`; swipe navigation is core. **Zoom**: plugin defaults carry the ruled gestures — double-click / double-tap toggle (2 stops), pinch + pan with bounds clamping, keyboard `+`/`-` (⌘/Ctrl `0` resets), Ctrl+wheel zoom; plain scroll pans when zoomed; no zoom options overridden at draft time. **Animations**: library defaults (fade 250 ms, swipe 500 ms, zoom 500 ms). **Scroll lock** is the library's (its `no_scroll` body class) — nothing to build. **Counter** (mosaic variant only): plugin defaults; styling per D8. **Index control**: the surface holds `index: number | null`; opening sets the clicked photo's index, `on={{ view }}` keeps it in sync while navigating, close resets to `null` — reopening starts at the clicked photo, not where the last open left off.

**D7 — Accessibility law.** **Dialog semantics** ship in the library root (`role="dialog"` + `aria-modal` + `aria-label` — verified in the shipped build); the `labels` prop tunes the strings if needed. **Keyboard**: Esc closes; ←/→ navigate; `+`/`-` zoom (⌘/Ctrl `0` resets); arrows pan when zoomed; Tab cycles the chrome controls (close, arrows, zoom). **Focus management**: focus moves to the lightbox container on open (library behavior); **focus restore on close is NOT provided upstream** — `PhotoViewer` adds the one wrapper effect: capture `document.activeElement` when `index` leaves `null`, restore it on close. This is the only focus work the spec adds by hand. **Visible focus**: every chrome control keeps a visible focus indicator (the library's focus-visible color change + the D8 app ring). **prefers-reduced-motion**: the library ships the media rule natively (`@media(prefers-reduced-motion)` unsets the portal fade, slide transitions, and loading-spinner animations — verified in the shipped stylesheet); the rendered-variants pass spot-checks the zoom animation under reduced motion, with the escalation `animation={{ zoom: 0 }}` behind a matchMedia check if it animates undesirably. **Touch**: swipe navigation + pinch zoom are core; the button/keyboard alternatives above cover the swipe-only paths.

**D8 — Theming.** The three stylesheets land in `apps/landing/src/styles.css` as bare `@import`s (the `@fontsource-variable/*` idiom): `yet-another-react-lightbox/styles.css`, `…/plugins/captions.css`, `…/plugins/counter.css` — followed by one scoped override block keyed on the library's `--yarl__*` variables. **The immersive stage stays near-black in both themes** — the deliberate, recorded exception to token-riding: photo viewing wants a constant dark stage (the library default backdrop), consistent with the dark theme's photo-dimming philosophy; a light-mode viewer that flashes white would be the jarring surface. The chrome ink (buttons, counter) keeps the library's white registers — legible on the dark stage in both themes. **The token-native parts** (the overrides block): the caption line re-registered to the wall's mono vocabulary (`.yarl__slide_description` via the library's description-color variable + font rules) and `:focus-visible` on `.yarl__button` gaining the app's focus treatment (`--brand-focus-ring` beyond the library's color change). Dark mode needs no special casing — the portal is a body child, so the `.dark` block's variables resolve inside it — but the rendered-variants pass verifies both themes anyway.

## Testing Decisions

A good test here pins externally observable contracts, not internals: what a caller gets from a seam, never how the seam is wired inside.

- **apps/landing lib-seams** (`src/lib/viewer.test.ts`, the plain-node seam style): `photoSlides` maps the alt law (title → alt, the `'Studio gallery photograph'` fallback), preserves order/count, and maps empty photos → empty slides; the captions law — `captions: true` + non-null caption → `description` set, null caption → absent, `captions: false` → `description` never set (the home law); the cover-slide seam — single slide, `alt` = package name, no description; the option constants — the cover variant's `finite` + hidden prev/next + no-Counter vocabulary, pinned like the other lib constants. Prior art: the landing lib-seam floor (`gallery-tabs.test.ts`, `mosaic.test.ts`; no component/DOM tests per the house rule).
- **Component behavior (open / zoom / navigate / close) is not unit-tested** — the house style keeps landing vitest to lib seams; the rendered-variants pass is the behavior gate.

## Out of Scope

- **Implementing the feature** — downstream: `/to-tickets` → SDD.
- **The other `CoverPanel` surfaces** (packages plates, home featured strip, branch strip) — they stay non-zoom; only the package-detail cover gains the viewer.
- **Image-dimension work or responsive `srcSet` variants on the public gallery wire** — the same-URL cache win (D5) is the accepted posture instead.
- **The admin (CMS) surfaces** — the viewer is landing-only.
- **The map's sibling features** — the services cover photos (#330's spec, already sliced) and the create-button polish (#335's spec) are separately-shippable specs, not this one's work.
