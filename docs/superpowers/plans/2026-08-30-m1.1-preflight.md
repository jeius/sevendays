# M1.1 — Pre-flight Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Land ticket #3 (M1.1): CI guardrails, env hygiene, config debt, and ADR-0007 — so the M1 data-layer work lands already guarded.

**Architecture:** Pure config/docs changes across the repo root and the two frontend app manifests — no application code. CI runs the exact gates developers run locally (`pnpm check` + `pnpm build`). Env examples document the two-connection-string topology that M1.3 will instantiate; ADR-0007 records why two URLs exist.

**Tech Stack:** GitHub Actions (pnpm 11 + Node 24), Turborepo, pnpm workspaces, Biome.

**Spec:** `docs/specs/2026-08-30-m1-real-data-layer-spec.md` (GitHub issue #2); ticket: GitHub issue #3. The plan argues from the spec's Implementation Decisions section ("Pre-flight (PR1)" and "Database connection topology (ADR-0007)") — executors read both.

## Global Constraints

- Node `>=24` (root `engines`); pnpm pinned via `packageManager` (`pnpm@11.24.0+sha512.bd27e…`) — CI installs pnpm from that field, never a hardcoded version.
- `pnpm-workspace.yaml` must NOT be touched: its `minimumReleaseAgeExclude: lucide-react@1.37.0` entry is what allows 1.37.0 to resolve; removing it now would silently downgrade on the next re-resolution.
- Never commit secrets or real connection strings; only the `.example` files are committed.
- Do not commit code that fails `pnpm check`.
- Commit subjects match existing history style (`ci:`, `chore:`, `build:`, `docs:`); use bullet bodies when the message is wordy.
- The user pushes and opens the PR (standing preference); the agent commits on the feature branch and hands off.
- `DATABASE_MIGRATE_URL` is the reserved name for the migration connection (M1.3 consumes it); `DATABASE_URL` stays the pooled runtime connection.

**Files:**

- Create: `.github/workflows/ci.yml`

**Interfaces:**

- Consumes: root `package.json` `packageManager` field (pnpm version source), `build:packages` script (must run before check — the shared config package's `dist/` is gitignored).
- Produces: the CI gate every later M1 ticket's PR must keep green; M1.4 will extend this workflow with a Postgres service container.

- [ ] **Step 1: Create the workflow file** with exactly:

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: pnpm

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      - name: Build shared config package
        run: pnpm build:packages

      - name: Lint, format, typecheck, test
        run: pnpm check

      - name: Build all apps and packages
        run: pnpm build
```

Notes for the executor: `pnpm/action-setup@v4` with no `version` input reads the pinned version from the root `packageManager` field — do not add a version. `node-version: 24` resolves the latest 24.x, satisfying `engines >=24`. No env/secrets are needed yet: the current test suite is the api health check, and the frontends build without Sentry/PostHog env (verified 2026-08-30 locally with no env files present). M1.4 adds the Postgres service container; don't preempt it.

### Task 5: ADR-0007 — database connection topology

**Files:**

- Create: `docs/adr/0007-database-connection-topology.md`

**Interfaces:**

- Produces: the decision record Tasks 2's examples and `docs/plan.md`'s checklist point at; M1.3's executor reads it before wiring connection strings.

- [ ] **Step 1: Create the ADR** (house style per ADR-FORMAT: short intro + optional sections only where they earn their place) with exactly:

```markdown
# Database connection topology

The runtime Worker cannot open raw TCP, so it must go through Supabase's transaction pooler (Supavisor, port 6543) — but drizzle-kit's `migrate` takes session-level advisory locks that break under transaction pooling. We keep two connection strings under two names: `DATABASE_URL` is the pooled connection, used by the deployed `apps/api` Worker (`wrangler secret put DATABASE_URL`), by local `wrangler dev` via its gitignored `.dev.vars`, and by the seed script; `DATABASE_MIGRATE_URL` is the direct connection (port 5432), used only by drizzle-kit (`db:generate` / `db:migrate` / `db:studio`) from `packages/db/.env`. The postgres client keeps `prepare: false`, which transaction pooling requires.

## Consequences

- Local dev runs against the remote Supabase project. The free tier pauses projects after ~1 week of inactivity — when local dev or the API suddenly can't connect, revive the project from the Supabase dashboard.
- Connection strings contain the database password: the operator pastes them into gitignored files and Worker secrets; they never enter chat, tickets, or the repo.
```
